# Research: Data Service API

**Date**: 2026-09-02 | **Spec**: [spec.md](spec.md)

---

## Decision 1 — Concurrency lock for in-memory claim store

**Decision**: Use `asyncio.Lock` with `async def` for `POST /claims`.

**Rationale**: FastAPI runs on an asyncio event loop (via Uvicorn). `async def`
endpoints execute on that loop and correctly `await` an `asyncio.Lock` without
blocking. Using `threading.Lock` inside an `async def` endpoint would block the
event loop thread while the lock is contended, starving all concurrent requests.
The alternative — `def` (sync) endpoints with `threading.Lock` — is also safe
(sync endpoints run in a thread pool), but carries unnecessary thread pool
overhead and is the non-idiomatic pattern for FastAPI.

For the practicum's in-memory dict mutation (no I/O, microsecond critical
section), `asyncio.Lock` is three lines and incurs no overhead.

**Alternatives considered**:
- `def` + `threading.Lock` — correct but slower (thread pool overhead per
  request); idiomatic for blocking I/O, not pure in-memory work
- No lock — incorrect; concurrent `POST /claims` requests could interleave dict
  mutations and drop records under CPython's GIL release points

**Spec correction**: The spec's `threading.Lock` language (FR-5 and NFR
"Concurrent write safety") should be updated to `asyncio.Lock`. This does not
change the functional requirement — only the implementation mechanism.

## Decision 2 — FastAPI startup data loading

**Decision**: Use FastAPI's `lifespan` context manager (FastAPI 0.93+) to load
all four JSON files at startup and store them in module-level dicts.

**Rationale**: The `lifespan` hook is the current idiomatic pattern for
application startup/shutdown logic in FastAPI (replaces deprecated
`on_event("startup")`). It runs before the first request is served, guaranteeing
data is available to all route handlers. Module-level dicts are the simplest
shared-state mechanism for a single-process service.

```python
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    _load_all_data()   # populate module-level dicts; log counts
    yield
    logger.info("Data Service shutting down")

app = FastAPI(lifespan=lifespan)
```

**Alternatives considered**:
- `@app.on_event("startup")` — deprecated since FastAPI 0.93; avoid
- Dependency injection with `lru_cache` — adds indirection for no benefit in a
  single-process, single-file service

## Decision 3 — In-memory store structure

**Decision**: Four module-level `dict[str, dict]` stores keyed by primary key.
No Pydantic model layer in the store — raw dicts loaded directly from JSON.

**Rationale**: The service's job is to load JSON and return JSON. Introducing
Pydantic models at the store layer would add schema validation on every read,
which is unnecessary — the seed data is trusted input generated by spec 004.
FastAPI will handle output serialization via `JSONResponse` or `dict` return.
Pydantic validation belongs at the request boundary (`POST /claims` body).

| Store | Key | Source file |
|---|---|---|
| `_members` | `member_id` | `members.json` |
| `_plans` | `plan_id` | `plans.json` |
| `_fee_schedules` | `procedure_code` | `fee_schedules.json` |
| `_claims` | `claim_id` | `claims.json` |

**Alternatives considered**:
- Pydantic models as store values — adds validation overhead on every load for
  no test benefit; seed data is pre-validated by spec 004
- Single combined store dict — reduces clarity; four stores named by domain are
  easier to reason about in route handlers
